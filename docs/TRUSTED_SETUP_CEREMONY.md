# Production Trusted Setup Ceremony Plan

> Tracking issue: [#595 — Add production trusted setup ceremony plan](https://github.com/collinsadi/opaque-stellar/issues/595)

The current circuit verifying keys were generated by a development ceremony
with a single contributor, which no mainnet deployment can credibly rely on.
A multi-party computation (MPC) ceremony distributes the toxic waste such that
security holds as long as at least one participant is honest and destroys their
randomness. This document plans the production ceremony end-to-end.

---

## Ceremony Design

### Protocol

**Powers of Tau** (phase 1, circuit-agnostic) followed by **circuit-specific
phase 2** using the Groth16 MPC protocol as implemented in `snarkjs`.

```
Phase 1: Powers of Tau  — circuit-independent; reuses any existing trusted
                          Powers of Tau up to 2^18 constraints (Hermez ceremony)
Phase 2: Circuit-specific — one contribution round per circuit variant;
                            must be conducted fresh for the production keys
```

Phase 1 may use a well-known existing ceremony (e.g., the Hermez Network
`powersOfTau28_hez_final_17.ptau`) to avoid running a new phase 1. The phase 1
artifact must be verified against its published checksums before use.

### Participant count

**Minimum: 6 independent participants.**

At least one participant must be:
- Based in a different legal jurisdiction from the Opaque team.
- Not affiliated with any other participant (employer, family, or financial relationship).
- Running a verified fresh machine (see §Machine Preparation).

Recommended distribution: 2 team members, 2 external protocol contributors,
2 independent community security researchers.

The ceremony coordinator (a team member) does not contribute randomness; they
only coordinate and verify. This keeps the coordinator's compromise from voiding
the ceremony.

### Security assumption

The ceremony is secure if **any single participant destroys their randomness**
after contributing. The ceremony documentation must clearly state this property
so the community can evaluate the participant list independently.

## Ceremony Phases

### Phase 0 — Preparation (T − 2 weeks)

- [ ] Identify and confirm 6+ participants; collect GitHub usernames and PGP
      key fingerprints.
- [ ] Publish the participant list and their PGP fingerprints in this document
      under §Participant Registry (see below).
- [ ] Agree on contribution sequence and deadlines.
- [ ] Prepare the coordination repo (private fork of this repo) where each
      contributor will push their transcript.
- [ ] Verify the phase 1 ptau artifact:
      ```bash
      sha256sum powersOfTau28_hez_final_17.ptau
      # compare against https://github.com/iden3/snarkjs/blob/master/README.md
      ```

### Phase 1 — Circuit Compilation

The coordinator compiles the final production circuits and begins phase 2:

```bash
circom circuits/stealth_attestation.circom --r1cs --wasm --sym \
  -o circuits/build/production

snarkjs powersoftau prepare phase2 \
  powersOfTau28_hez_final_17.ptau \
  circuits/build/production/pot17_final.ptau \
  -v

snarkjs groth16 setup \
  circuits/build/production/stealth_attestation.r1cs \
  circuits/build/production/pot17_final.ptau \
  circuits/build/production/stealth_attestation_0.zkey
```

The initial `.zkey` (`_0.zkey`) is published to the ceremony repo with its
SHA-256 checksum.

### Phase 2 — Contribution Rounds

Each participant, in sequence:

1. Downloads the previous `.zkey` and verifies its checksum.
2. Prepares a fresh machine (see §Machine Preparation).
3. Contributes randomness:
   ```bash
   snarkjs zkey contribute \
     stealth_attestation_<N>.zkey \
     stealth_attestation_<N+1>.zkey \
     --name "<Participant Name>, <Date>" \
     -v
   ```
4. Records the contribution hash (printed by snarkjs).
5. Deletes their randomness: `shred -uz <entropy_source>` or equivalent.
6. Publishes their `.zkey` to the ceremony repo with their PGP signature.
7. Publishes a signed attestation (see §Contribution Attestation).

The coordinator verifies each contribution before passing to the next participant:

```bash
snarkjs zkey verify \
  circuits/build/production/stealth_attestation.r1cs \
  circuits/build/production/pot17_final.ptau \
  stealth_attestation_<N+1>.zkey
```

### Phase 3 — Finalisation

After all contributions:

```bash
snarkjs zkey beacon \
  stealth_attestation_<last>.zkey \
  stealth_attestation_final.zkey \
  <beacon_hash> \
  10 \
  -n "Final beacon — Ethereum block hash TBD"
```

The beacon hash is taken from a future Ethereum block (announced at least 24
hours before finalisation) so no participant can predict or manipulate it.

Export the final verifying key:

```bash
snarkjs zkey export verificationkey \
  stealth_attestation_final.zkey \
  verification_key.json
```

Compute the verifying key hash:

```bash
sha256sum stealth_attestation_final.zkey verification_key.json
```

Record both in `deployments/mainnet/stealth_attestation_v<N>.json` under
`zkey_sha256` and `vk_hash` respectively.

## Machine Preparation

Each contributor should:

1. Use a **fresh operating system** (live boot recommended: Ubuntu 24.04 LTS
   on a USB drive, or a freshly provisioned cloud VM with attested boot).
2. Install only `node`, `snarkjs`, and dependencies from the package-lock.
3. Perform the contribution **offline** if possible (download zkey first, air-gap, contribute, upload).
4. Delete the machine image or destroy the VM after confirming the upload.

Contributors choosing a cloud VM must use a provider that supports attested
delete (e.g., AWS EC2 with instance termination confirmed in CloudTrail) and
must include the VM instance ID in their attestation.

## Transcript Publication

The ceremony transcript is published to the `circuits/ceremony/` directory:

```
circuits/ceremony/
  participants.md          — participant list with PGP fingerprints
  attestations/
    01_<handle>.md         — signed attestation per contributor
    02_<handle>.md
    ...
  checksums.sha256         — SHA-256 of every .zkey file in the chain
  beacon.txt               — Ethereum block number, hash, and timestamp used for beacon
  final_vk.json            — exported verification key (symlink to verification_key.json)
```

### Verification script

Third parties can verify the full transcript independently:

```bash
node circuits/scripts/verify_ceremony.mjs \
  --r1cs circuits/build/production/stealth_attestation.r1cs \
  --ptau circuits/build/production/pot17_final.ptau \
  --ceremony-dir circuits/ceremony/ \
  --final-zkey circuits/ceremony/stealth_attestation_final.zkey
```

The script checks:
- Each contribution's hash matches the snarkjs `zkey verify` output.
- The chain of `.zkey` files is contiguous (no gaps).
- The beacon block hash matches the published Ethereum block.
- The final `verification_key.json` matches `sha256sum` in `checksums.sha256`.

The script prints `✓ ceremony valid` or a specific failure line. It has no
network dependencies once the `.zkey` files are present.

## Key Rollover from Development Keys

The current development keys (`circuits/fixtures/`) are used for testnet and
local development only. The rollover to production keys follows the migration
process defined in `CIRCUIT_VERSIONING.md`:

1. Production ceremony completes; `stealth_attestation_final.zkey` and
   `verification_key.json` are published with verified checksums.
2. The admin registers the new verifier on mainnet:
   `register_verifier(version_id = 1, vk_hash, vk_bytes)`.
   (This is the first mainnet registration; the development keys were never
   deployed to mainnet.)
3. Testnet gets the same registration at the same time to keep environments in sync.
4. The frontend switches to the production `.zkey` URL for proof generation.
5. The development key files remain in `circuits/fixtures/` for local test
   purposes but are never used for a network with real funds.

There is no coexistence window needed for this initial rollover because no
mainnet notes exist under the development keys. Subsequent circuit upgrades
follow the 30-day coexistence window policy in `CIRCUIT_VERSIONING.md`.
